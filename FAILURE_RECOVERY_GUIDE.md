# FAILURE_RECOVERY_GUIDE

How the backend behaves when things go wrong, what the client is told, and how to test it. Status words: **Tested** = an automated test in `tests/` covers it. **Implemented** = code exists but no automated test. **Not implemented** = the feature does not exist yet. Nothing here promises uninterrupted service: Render Free and Atlas M0 can and will interrupt us.

## The three rules everything rests on
1. **The database is the truth.** Every accepted move is ONE conditional `updateOne` on the game document (D-011). The server acknowledges and broadcasts a move only after that write succeeded. If the write fails, the client gets `TEMPORARILY_UNAVAILABLE` and nothing changed.
2. **RAM holds only timers and "who is connected".** Timers are rebuilt from the database at boot (`monitor.recover()`); every timer callback re-reads the database before acting.
3. **Clients retry with the same `moveId`.** A move that is already stored is acknowledged again with `duplicate: true` and never applied twice.

## Clock and disconnect policy (D-012, D-013, D-024; values are env variables)
| Situation | What happens |
|---|---|
| One player disconnects, server healthy | Their clock keeps running. They have 60 s (`GAME_RECONNECT_GRACE_MS`) to return. Opponent gets `game.opponent.disconnected`. After 60 s: opponent wins by `abandoned` (fewer than 2 moves: game `aborted`, no rating change). |
| Both players disconnect, server healthy | Game becomes `paused_disconnect`. Clocks are charged up to that moment, then frozen. |
| Server restart/crash, or MongoDB came back after an outage | Every `active` game becomes `paused_server_recovery` with its last confirmed clock snapshot. **Downtime is not charged.** The game resumes only when BOTH players are connected again. |
| A paused game waits 5 min (`GAME_PAUSED_HOLD_MS`) | If one player is present: they win by `abandoned`. If nobody: draw `both_abandoned` (fewer than 2 moves: `aborted`). |
| A `paused_disconnect` game and ONE player returns | Play resumes immediately; the absent player has the normal 60 s grace. |
| Clock snapshots | Written with every accepted move and every 5 s (`GAME_CHECKPOINT_INTERVAL_MS`) while active. After a crash the restored clock can be up to one checkpoint interval behind real time, so the side to move may get back up to 5 s of thinking time; it is never charged more than it used. |

Edge cases and limits to know:
- The hold timer restarts at every boot, so a game can wait longer than 5 min in total if the server keeps restarting. It is always settled eventually (Tested: `game-recovery-paused.test.js`).
- On a graceful shutdown (SIGTERM) sockets are closed with code 1001; whether both disconnect handlers pause the game before the process exits, or boot recovery does it, is **not tested**. Either way the game ends up paused with its clock snapshot.
- Insufficient-material timeouts are not handled (D-021). Draw and checkmate outcomes are reported by the client and trusted.
- Rating update is at-most-once: a crash between claiming the update and applying it loses that one change.

## The 25 scenarios

**1. Render Free sleeps** (about 15 minutes without traffic; the next request takes up to about a minute to wake it). Cause: free instances are spun down. Server: nothing to do; at wake-up boot recovery runs. Client: treat connection failures as "server waking up": call `GET /health/live` every few seconds with back-off, then reconnect, then follow the reconnect procedure in WEBSOCKET_DOCUMENTATION. Status: recovery Tested by simulation; real Render behaviour **not yet verified** (not deployed). Tip: an external pinger would keep it awake but is a paid-plan-like workaround and still gives no uptime guarantee.

**2. Render restarts the server** (deploys, maintenance, free-tier restarts). Server: SIGTERM, sockets closed with 1001, boot recovery pauses live games. Client: on close code 1001 or any drop, reconnect with back-off. Status: boot recovery Tested; graceful shutdown path Implemented, not tested.

**3. Node.js crashes during a game.** Cause: unhandled exception. There are no global `uncaughtException` handlers, so the process exits and Render starts it again. Server: boot recovery (`paused_server_recovery`, clocks restored, resume when both are back). Client: same as 2. Status: Tested by simulating the crash inside a test (`monitor.stop()` plus dropping sockets); a real `kill` is covered by the manual procedure below.

**4. Server unresponsive.** Cause: blocked event loop or hung process. Server: `render.yaml` sets `healthCheckPath: /health/live`; Render restarts an instance that fails it. Then as in 3. Status: Implemented; not tested.

**5. Both players lose connection.** See the policy table. Status: Tested (`game-presence.test.js`).

**6. One player loses internet.** See the policy table. The other player is told with `game.opponent.disconnected { graceMs }`. Status: Tested.

**7. WebSocket disconnects unexpectedly.** Same as 5/6, depending on who is left. Client: reconnect, `auth`, `game.join`, resync. Status: Tested.

**8. WebSocket connected but silent.** Server pings every 30 s (`WS_HEARTBEAT_INTERVAL_MS`); a socket that did not answer the previous ping is terminated and then handled as a disconnect. Status: Tested.

**9. Player reconnects repeatedly.** Each reconnect cancels the grace timer and sends `game.active`; no duplicate game or double notification. Status: Tested.

**10. Client retries a move after losing the ack.** Resend the same `moveId` and `seq`. Server returns the original ack with `duplicate: true`, even if the game moved on or ended. Status: Tested.

**11. Same move submitted twice.** Same mechanism as 10. A `moveId` used by the OTHER player gives `DUPLICATE_MOVE_ID`. Status: Tested.

**12. Two devices as the same account.** The newest device that sends `game.join` controls the game; the older device gets `game.session.replaced` and `SESSION_REPLACED` on moves. Status: Tested.

**13. Two simultaneous requests modify one game.** The conditional update matches only if status, `seq`, side to move and "moveId not stored" are unchanged; exactly one wins, the other gets `STALE_SEQ`, `NOT_YOUR_TURN` or `CONFLICT`. Status: Tested.

**14. MongoDB temporarily unavailable.** `bufferCommands=false` (D-009) makes queries fail fast. Moves get `TEMPORARILY_UNAVAILABLE` (retry the same request). When the driver reconnects, live games are paused and resumed without charging the outage. `/health/ready` returns 503 meanwhile. Status: write failure, read failure and the reconnect event are Tested; a real Atlas outage is **not tested**.

**15. MongoDB connection pool exhausted.** Pool size is `MONGODB_MAX_POOL_SIZE` (default 10). Excess requests wait and may time out, which becomes `TEMPORARILY_UNAVAILABLE`. Status: Implemented; not tested, not load-tested.

**16. MongoDB storage or free-tier limits reached.** Atlas M0 has 512 MB of storage and shared, throttled resources. Writes would fail and look like 14. Mitigation: TTL on `game_events` (90 days), `matchmaking_queue`, `sessions` (30 days after expiry) and `invitations`, plus a cleanup job (D-060) every 6 hours that empties the move list of finished games older than 90 days (the PGN stays) and deletes resolved reports older than 365 days. Whole games and personal messages are never deleted (D-028), so the server also watches the size: every hour it reads the database statistics (data + indexes) and logs a WARNING at 80% and an ERROR at 90% of `STORAGE_LIMIT_MB` (default 512). `GET /health/storage` shows the same level (always HTTP 200). The number is an estimate: Atlas may count storage differently, so treat the 80% warning as the signal to act (archive old games, or upgrade the cluster). What to do when `critical`: check the Atlas dashboard storage chart, then archive or upgrade. The monitor never deletes anything; the cleanup job is separate. To see what the cleanup would change: `node scripts/retention.js` (dry run, changes nothing) or `GET /api/v1/admin/retention`; `node scripts/retention.js --apply` does it by hand. A removed move list can only be restored from a backup. The job can be switched off with `RETENTION_ENABLED=false` or made log-only with `RETENTION_DRY_RUN=true`. Retention is Tested (`tests/retention.test.js`, 12 tests, database only); the 6-hour timer itself (`tick()` is tested directly), a run on real Atlas data and the TTL monitor deleting a real 30-day-old session are **not** verified. Status: the monitor and endpoint are Tested with a stubbed database size (levels, 200 when critical, database down, failing stats call). A real full Atlas cluster is **not tested**, so the exact error clients get when Atlas refuses writes is unverified; the design assumes it surfaces as `TEMPORARILY_UNAVAILABLE` like scenario 14.

**17. Render completely unavailable.** Data is safe in Atlas. Deploy the same repository elsewhere with the same environment variables (SERVER_SETUP_GUIDE section 7, "Move to another host"). If the Atlas data itself were gone, restore the latest backup (scenario 25e). The first boot there pauses all live games without charging time. Status: design only.

**18. A deployment introduces a bug.** Run `npm test` before every push. On Render use the dashboard's rollback to the previous deploy. Games survive because state is in the database. Status: process, not code.

**19. Restart during a tournament (Phase 7c, D-052 to D-055).** Cause: Render restarts or sleeps, or the process crashes while a tournament is waiting to start or running. Rule: ALL tournament state is in MongoDB (`tournaments`, `tournament_players`, the coin ledger and `games`); RAM holds only a timer that calls `tick()` every `MATCH_TICK_MS`. Standings are recomputed from stored pairings, never kept as counters.
Server behaviour, one case at a time:
- Down at `startsAt`: the next tick after boot starts it (late, never lost). Fewer than 4 players: cancelled and every fee refunded.
- Down while a round is running: the pairings and their games are stored. A game that was `active` becomes `paused_server_recovery` through the normal game recovery (no downtime is charged to the clocks) and the pairing stays `playing`. When the game ends, its result is recorded.
- A game finished while the server was down, or finished but not yet recorded: the sweeper reads the games of unfinished pairings and records the result. Recording is a conditional update (`pairing.status != done`), so a result is applied once.
- Crash between creating a game and linking it to its pairing: the game carries the pairing key and a unique index allows one game per pairing, so the sweeper finds and links the existing game instead of creating a second one.
- Two sweepers or two ticks at once (a slow tick, overlapping calls): every step is a conditional update or an idempotent call; one game and one notification per pairing (Tested with six simultaneous sweepers plus the real one).
- Crash after charging an entry fee but before the join finished: the sweeper withdraws the stale join and refunds it once. A refund or a prize that failed is retried on every tick; ledger keys (`tournament:<id>:entry|refund|prize:<user>`) make a double payment impossible.
- Show-up: the 3 minute `startBy` is a stored timestamp, so a restart does not reset it. A player who is not online and free when it expires loses the pairing (both absent: both score 0). A pairing that already has a game is never forfeited, because the game's own clock and disconnect rules decide it.
Client: a user who was offline reads `GET /api/v1/notifications` and `GET /api/v1/tournaments/:id` after reconnecting; round and game-ready notifications are stored, not only pushed.
Limits: a round can start up to one tick (2 s default) late; a player who is online but still inside another game when `startBy` expires counts as absent; there is no manual admin repair yet (Phase 8).
Status: **Tested** in `tests/tournaments.test.js` (19, including the sweeper-down, many-sweepers, crashed-join and failed-refund cases, simulated by writing the half-done states by hand) and `tests/tournaments-logic.test.js` (14). **Not verified:** killing the real process during a real tournament (the manual kill test only covers a single match), the 2 s timer itself (its `tick()` is tested directly), behaviour on Atlas, a real Android client.

**20. Temporary chat lost in a restart.** Match chat is implemented (D-032): relayed in RAM, never stored, so after a restart or the end of the game it is gone by design. Server: an offline opponent means the message is dropped (`delivered: false`), never queued; after the game ends sending returns `GAME_OVER`. Client: show chat as "this game only", keep a local copy for display, never expect it back after a reconnect. Status: Tested (`tests/match-chat.test.js`, includes "stored nowhere in the database"). Room chat: Phase 5, not implemented. Permanent personal messages are different: they survive restarts, and a retry with the same `clientMessageId` never duplicates (`tests/messaging.test.js`).

**20b. Analysis rooms and a restart (Phase 5, D-035 to D-040).** The room (members, roles, invitations, variations, annotations, shared position) is one MongoDB document and survives any restart; nothing in it depends on RAM. What is lost on a restart: which sockets are "in" a room (presence) and room chat. Server: after a restart `room.state` still works; an edit or chat from a socket that has not sent `room.join` gets `ROOM_NOT_JOINED`, so a client that did not re-join is told instead of silently missing events. Client: on every reconnect send `room.join` for the open room, replace local state with `room.state`, ignore pushes whose `rev` is not newer, and treat a gap in `rev` as "join again". Two people editing at once: every change is one write guarded by `rev` (retried up to 5 times, then `ROOM_BUSY`), so changes are never lost or applied twice; the 10-member limit is enforced by the same check. Database down: the change is NOT applied and the client gets `TEMPORARILY_UNAVAILABLE` (repeat it). Abandoned rooms are closed after 24 h without activity and nobody joined, and deleted 7 days after closing. Status: Tested (`tests/rooms.test.js`, `tests/room-analysis.test.js`, including a simulated restart that clears presence). Not tested: a real Atlas outage during a room edit.

**21. TURN unavailable.** Voice signaling is implemented (D-027, D-033). Cause: TURN is not configured, the provider is down, or its free relay quota is used up. Server: `voice.config` returns STUN only and `turnAvailable: false` when `TURN_URLS` is unset; with TURN configured it returns provider credentials (time limited when `TURN_SECRET` is used). Calls between peers that cannot connect directly fail; the client reports `voice.failed`, the opponent receives `voice.ended { reason: "ice_failed" }`, and the reply carries `turnAvailable` so the app can explain. The game itself never depends on voice. Status: signaling and credential logic Tested (`tests/voice.test.js`, `tests/voice-turn.test.js`); real audio, real NAT behaviour and a real Metered account are **not verified** (needs the Android client and a TURN account).

**22. Many users connect at once.** Limits: 300 REST requests/minute/IP, 20 auth requests/15 min/IP (shared by players behind one NAT), database pool of 10. Free Render has little CPU and RAM. Status: **not load-tested**; the target is about 40 users.

**23. Malicious or oversized WebSocket messages.** Frames above `WS_MAX_PAYLOAD_BYTES` (16 KB) close the socket with 1009; invalid JSON and unknown events get an `error` and do not close it; every payload is validated with Zod; unauthenticated sockets can only `auth` and `ping` for 10 s. Status: Tested. **Gap:** there is no per-socket message rate limit yet (planned Phase 8).

**24. Tokens expire during a live session.** The server sends `auth.expiring` 30 s before expiry; the client refreshes over REST and sends `auth` again on the same socket. Without it the server replies `TOKEN_EXPIRED` and closes with 4002 after 30 s. Games are not affected, because they live in the database. Status: Tested.

**25. Access to another user's private game or messages.** Games: any non-player gets `GAME_NOT_FOUND` (same answer as "does not exist") over REST and WebSocket. Personal messages: a conversation that belongs to other users answers `CONVERSATION_NOT_FOUND`, the same as a missing one, and only friends can message each other (`NOT_FRIENDS`). Match chat and voice: non-players get `GAME_NOT_FOUND`. Analysis rooms: a non-member, a removed member and an unknown id all get `ROOM_NOT_FOUND` over REST and WebSocket. Status: Tested for games, messages, match chat, voice and rooms.

**25b. Spectators, game history and saved analysis (Phase 6, D-041 to D-044).** Access: a live game can be followed only by a friend of a player with no block either way; strangers, blocked friends and unknown ids all get `GAME_NOT_FOUND`, and spectators cannot play, resign or chat as players (`GAME_NOT_FOUND`). Completed games over REST follow the same rule; a stranger gets 404 for them too. Saved analyses belong to their owner only (`ANALYSIS_SESSION_NOT_FOUND` for anyone else); saving a room needs membership (`ROOM_NOT_FOUND` otherwise). Restart: who is watching is RAM only, so after a restart every spectator must send `spectate.join` again (the game itself, paused by recovery, is in MongoDB); history and saved analyses are plain MongoDB reads and survive any restart. Database down: spectator pushes still work for games already running, but `spectate.join`, history and saved analysis answer `503 TEMPORARILY_UNAVAILABLE`; retry. Spectator flood: at most 20 users per game (`SPECTATOR_LIMIT`), `spectate.join` is limited to 10 per 10 s per socket. Dropped connection: the subscription is removed immediately and the players get a new `spectate.count`. Status: Tested (`tests/spectators.test.js`, `tests/game-history.test.js`, `tests/analysis-sessions.test.js`). **Not tested:** a restart with active spectators, a database outage during `spectate.join`, many spectators at once on Render Free, a real client.

**25d. Notifications (Phase 7b, D-051).** Stored first, pushed second: a crash between the two loses only the live push, and the client catches up with `GET /api/v1/notifications` after every reconnect. A module that repeats itself after a restart passes a `key`, so one event creates one notification (Tested, including ten simultaneous creates). A database failure makes `notify()` return null and `create()` answer `TEMPORARILY_UNAVAILABLE`; nothing is stored or pushed and the same call works once the database is back (Tested). Notifications are private: another user gets `404` (Tested). NOT covered: phone push while the app is closed (needs Firebase, D-051 is still open).

**25c. Coins, purchases and a crash (Phase 7a, D-046 to D-050).** Rule: money and items move exactly once. Every coin change is a ledger row with a caller-chosen unique `key` plus ONE conditional update of the wallet (D-046); the wallet remembers the last 50 applied transaction ids and the unique ledger key protects older ones. There are no MongoDB transactions, so the design assumes a crash can happen between any two steps, and the clean-up (`wallet.reconcile`, run every `WALLET_RECONCILE_INTERVAL_MS`, default 30 s, on rows older than `WALLET_PENDING_AGE_MS`, default 60 s) finishes the job:
| Crash happens | State left behind | What the user sees | Recovery |
|---|---|---|---|
| Before the ledger row exists | nothing | the request fails; nothing changed | client retries the same request |
| After the row, before the wallet changed | row `pending`, wallet untouched | not charged, nothing granted | a retry continues it; the clean-up applies a stale CREDIT and discards a stale SPEND |
| After the wallet changed, before the item was granted | row `pending`, id already in the wallet | charged, item missing | the retry or the clean-up re-runs the idempotent grant; never charges twice |
| After the item was granted, before the row was marked | same as above | charged, item present | harmless re-run |
Purchases (real money): the app sends only `productId` and `purchaseToken`; states are `verified` -> `granted` -> `acknowledged` and every step is idempotent. Store unreachable while verifying: `503 PURCHASE_VERIFICATION_UNAVAILABLE`, nothing stored, retry the same request. Store unreachable when acknowledging or consuming: the user keeps the item, the reply says `finalized: false`, and the clean-up retries (Google refunds purchases that are never acknowledged, so this retry matters). Crash after the store said yes but before the item was granted: the clean-up grants it once, and a later redeem of the same token answers `duplicate: true`. Simultaneous identical requests (ten at once) credit once; simultaneous spends can never push a balance below zero. A database outage gives `TEMPORARILY_UNAVAILABLE`: retry the same request. Ledger rows are never deleted, so they count towards the storage watch of scenario 16.
Status: **Tested** with `tests/economy.test.js` (21) and `tests/purchases.test.js` (14), using simulated crashes (rows written by hand in the half-done states above) and the fake store. **Not verified:** the `google` verifier against real Google Play (no account yet, and no automated test of its HTTP layer), a real Atlas outage during a purchase, the periodic timer itself (`economy.monitor`; its two functions are tested directly), a real Android client.

**25e. Data lost or damaged (a bug, a mistaken command, a bad cleanup) and backups (Phase 8e, D-061).** Cause: anything that changes MongoDB data wrongly; Atlas M0 keeps no backups of its own. Expected behaviour: the owner restores from a backup made earlier with `node scripts/backup.js`. The restore checks every file against the manifest (checksum and document count) BEFORE it touches the database and refuses a damaged or unfinished backup; it is a dry run unless `--apply`; it refuses to change a collection that already has documents unless `--replace`; it cannot be tricked into reading files outside the backup folder (a damaged manifest is rejected). Client: stop the server first (clients see the server as down, then reconnect; live games are paused by boot recovery without charging clock time, D-012). Everything written after the backup is lost, so make backups weekly and before risky steps (the first retention `--apply`, a restore, a migration). After a restore the server recreates the indexes when it starts. Status: Tested (`tests/backup-restore.test.js`, 15: round trip with ids and dates intact, dry run, refusal on non-empty collections, `--replace`, `--only`, damaged, truncated, missing and unfinished backups, unsafe manifest, several insert batches, a 1 MB document, an empty database) and the two scripts were run end to end on the local development database (backup, dry run, refused `--apply`). **Not tested:** a real backup or restore on Atlas, a large database (the backup streams, so memory should stay small, but time and size are unmeasured), a restore while the server is running (the guide says to stop it first), and the restore-then-start-server index rebuild as one scripted sequence.

## Manual test: kill the server during a live match (Windows)

**Easy way (recommended):** stop your normal server (click its terminal tab, press Ctrl+C), then run `node scripts/manual-kill-test.js` in the project folder. The script starts its own server on port 3100, plays two moves, kills the server process with no warning, waits 12 seconds, starts it again and prints PASS or FAIL for each check. It creates two test users (names start with `kt`) in your database and deletes nothing. If a line says FAIL, copy the whole output and send it to me.

The hand-typed version below does the same thing step by step, if you want to see the raw messages.

Needs: the server running locally with a working `.env`, and two WebSocket clients. Install once: `npm install -g wscat`.

1. Terminal A: `npm start`. Wait for "server listening" and "game recovery finished".
2. Create two users (PowerShell), save the `accessToken` of each:
   `Invoke-RestMethod -Method Post -Uri http://localhost:3000/api/v1/auth/register -ContentType 'application/json' -Body '{"email":"a@example.com","username":"playera","password":"Passw0rd!long"}'`
   Repeat with `b@example.com` / `playerb`. (Password 8-72 characters, username 3-20 letters, digits or underscores. The reply contains ccessToken.)
3. Terminal B and C: `wscat -c ws://localhost:3000/ws`. In each, send `{"id":"1","type":"auth","payload":{"accessToken":"<accessToken>"}}`.
4. In both: `{"id":"2","type":"queue.join","payload":{"timeControl":"5+0","rated":false}}`. Each receives `game.started` with the `gameId` and `yourColor`.
5. White sends a move, for example `{"id":"3","type":"game.move","payload":{"gameId":"<id>","moveId":"manual-move-0001","seq":0,"uci":"e2e4","san":"e4","fen":"rnbqkbnr/pppppppp/8/8/4P3/8/PPPP1PPP/RNBQKBNR b KQkq e3 0 1"}}`. White gets `game.move.ack`, black gets `game.move`. Black replies with `e7e5` (`seq` 1, new `moveId`, FEN from the table in `tests/gameHelpers.js`).
6. **Kill the server without warning.** In a new PowerShell window run `Get-NetTCPConnection -LocalPort 3000 -State Listen | Select-Object -ExpandProperty OwningProcess` to get the server's process number, then `Stop-Process -Id <that number> -Force`. This stops only the server. Do NOT press Ctrl+C: that is a graceful shutdown, a different test.
7. Both wscat windows drop. Wait about 30 seconds (the "downtime"). Write down the clocks you last saw.
8. Terminal A: `npm start` again. The log must say `live games paused and restored after outage` or `game recovery finished` with `games: 1`.
9. Reconnect both wscat clients, send `auth` again, and watch for `game.active`. Then send `{"id":"4","type":"game.join","payload":{"gameId":"<id>"}}` from each.
10. Expected: `game.state` shows `status: "paused_server_recovery"`, `seq: 2`, both moves, and clocks equal to the snapshot (within the 5 s checkpoint interval), NOT reduced by the 30 s downtime. When the second player has reconnected, both receive `game.resumed` and the clock of the side to move runs again.
11. Lost-ack test: stop the server again right after a move, restart, rejoin, and resend the same move with the same `moveId`. Expected: either `duplicate: true` (the move had been stored) or a normal ack (it had not). The board must never contain the move twice.
12. Settle test: after a restart connect only ONE player and wait 5 minutes. Expected: `game.over` with `resultReason: "abandoned"` and that player winning.
